# 5분 발표 대본

> 광주 4반 G123 신민서  
> 주제: 이미지 기반 제품 결함 판정 및 근거 검증 멀티에이전트

이 문서의 수치는 고정 dev 52장의 실모델 결과다. `ABSTAIN`, 오류,
누락을 전체 분모에 포함했다. A+는 결과를 본 뒤 설계한 dev 후분석
후보이며, 원래 A의 성공 결과나 held-out 성능으로 설명하지 않는다.

## 슬라이드 1. VLM 판정에 근거와 승인 절차를 추가했습니다 (35초)

### 화면

- 이미지 기반 제품 결함 판정 및 근거 검증 멀티에이전트
- 광주 4반 G123 신민서
- 문제: 범용 VLM은 작은 결함을 놓치거나 오판을 확신하여 말할 수 있다.
- 목표: 관찰, 기준서 확인, 규칙 판정, 사람 승인을 추적 가능한 검사 절차로 연결한다.

### 대본

> 안녕하세요. 광주 4반 G123 신민서입니다. 제 프로젝트는 이미지 기반
> 제품 결함 판정 및 근거 검증 멀티에이전트입니다. 범용 VLM은 별도
> 학습 없이 제품 이미지를 설명할 수 있지만, 정상 제품을 불량으로 보거나
> 미세 결함을 놓칠 수 있습니다. 그래서 VLM 하나에게 최종 판정을 맡기지
> 않고, 관찰부터 사람 승인까지 추적할 수 있는 검사 절차를 구현했습니다.

## 슬라이드 2. 에이전트별로 관찰과 판정 책임을 나눈습니다 (50초)

### 화면

1. Observer: 정상 참조와 전체·분할 이미지 관찰
2. Cross-Checker: 반전 이미지의 6개 결함 항목 별도 확인
3. Spec-Judge: 검사 기준서 RAG top-3 검색과 조항 판단
4. 코드 결정표: `PASS / REJECT / ABSTAIN`
5. HITL과 validate: 사람 승인과 관찰·조항 인용 검증

기술 요소: LangGraph, MCP, RAG, 의존성 주입, LangSmith trace, SQLite
checkpointer, 단위·통합 테스트

### 대본

> Observer는 정상 참조와 검사 이미지를 전체 및 분할 영역으로 관찰합니다.
> Cross-Checker는 같은 이미지를 반전하고 여섯 개 결함 항목을 별도로
> 확인합니다. Spec-Judge는 이 관찰문만 사용해 품목별 검사 기준서의
> 상위 조항을 RAG로 찾습니다. 최종 결과는 LLM이 아니라 코드 결정표가
> 판정합니다. 근거가 충분하지 않거나 충돌하면 ABSTAIN으로 보류하고,
> 사람 승인 후 보고서의 관찰문과 기준서 인용을 다시 검증합니다.

## 슬라이드 3. 보류와 실패를 빼지 않고 검증했습니다 (50초)

### 화면

- MVTec AD 4개 품목
- 고정 dev 52장에 대한 B0·A 동일 이미지 비교
- `ABSTAIN`, 오류, 누락을 전체 분모에 포함
- 전체 회귀 `685 passed`
- held-out 140장 미사용
- RAG top-3 hit rate: `nomic 60.71%`, `bge-m3 82.14%`

### 대본

> MVTec AD의 외부 라벨을 사용해 단독 VLM B0와 전체 에이전트 A를
> 동일한 dev 52장에서 비교했습니다. 오류, 누락, ABSTAIN을 제외하지
> 않아 자동 처리 성능이 부풀려지지 않게 했습니다. 결정표, 경계값,
> 동등 분할, 결함 주입, 상태 전이를 포함한 회귀 테스트 685건을
> 통과했습니다. 이전 R6에서 저장된 실제 query의 오프라인 embedding
> 후보 비교에서는 bge-m3가 nomic보다 21.43퍼센트포인트 높았습니다.
> 정식 A 실행은 nomic을 사용했고, 이 수치는 RAG 컴포넌트의 후속 후보이며,
> 최종 판정 정확도 향상을 의미하지는 않습니다.

## 슬라이드 4. 원래 A는 실패했고, 사후 결합은 다음 검증 후보입니다 (65초)

### 화면

| 지표 | B0 단독 VLM | A 원래 에이전트 | A+ 사후 결합·미통합 |
|---|---:|---:|---:|
| Accuracy | 28.85% | 11.54% | 38.46% |
| Balanced Accuracy | 26.79% | 12.50% | 37.20% |
| 정상 정답 / 24 | 0 | 6 | 5 |
| 결함 정답 / 28 | 15 | 0 | 15 |
| `ABSTAIN` / 52 | 29 | 41 | 23 |
| Coverage | 44.23% | 21.15% | 55.77% |

아래에 크게 표시:

- 원래 A: 정확도 향상 가설 `NO-GO`
- A+ 사후 결합: B0 대비 Accuracy `+9.62%p`, Balanced Accuracy `+10.42%p`
- B0 대비 McNemar exact `p=0.0625`, held-out 미검증, 성능 입증 아님
- 실제 결함 1건 오합격, B0+A 이중 실행, 그래프·UI 미통합

### 대본

> 원래 전체 에이전트 A의 정확도는 11.54퍼센트로 B0보다 낮았습니다.
> A는 정상 여섯 장을 맞혔지만 결함 28장을 한 장도 확정하지 못했고,
> 41장을 보류했습니다. 따라서 에이전트가 단독 VLM보다 정확하다는
> 원래 가설은 실패했습니다. 저장된 같은 출력에서 B0의 REJECT를 우선하고
> 그 외에는 A의 PASS만 채택하는 cascade A+ 후보는 Accuracy 38.46퍼센트,
> Balanced Accuracy 37.20퍼센트를
> 보였습니다. B0보다 각각 9.62, 10.42퍼센트포인트 높지만,
> 결과를 본 후 dev에서 만든 후분석 후보이고 p-value도 0.0625로
> 통상적인 0.05 기준을 통과하지 못했습니다. 실제 결함 한 건을 PASS로
> 바꾼 위험도 있고, B0와 A를 모두 실행하며 현재 그래프에는 통합하지
> 않았습니다. 따라서 별도 계획을 동결해 다시 검증하기 전에는 성능
> 향상을 입증했다고 말할 수 없습니다.

## 슬라이드 5. 검사 흐름은 완성했고 시각 모델은 교체가 필요합니다 (40초)

### 화면

- 구현 성과: 근거·조항·승인 이력이 남는 검사 흐름
- 실측 결론: `qwen2.5vl:3b` 기반 원래 A는 성능 `NO-GO`
- 다음 검증: 강한 Observer, 서로 다른 Cross 모델, 전용 이상탐지 신호
- 제출 시점 한계: A+는 dev 후분석이며 held-out 결론은 아님

### 대본

> 이번 프로젝트로 관찰, 기준서 검색, 규칙 판정, 사람 승인, 보고서
> 검증이 이어지는 검사 흐름을 구현했습니다. 반면 현재 3B 시각 모델으로는
> 원래 A의 정확도 개선에 실패했습니다. 다음 검증에서는 더 강한 VLM을
> Observer에 적용하고, Cross에 다른 모델을 사용해 판단 독립성을 확보해야
> 합니다. PatchCore 같은 전용 이상탐지 점수를 시각 근거로 추가하고,
> VLM은 결함 설명과 기준서 연결을 담당하는 구조가 적합합니다. A+는 가능성을
> 본 dev 후보이며, 제출 시점에서 검증된 최종 결론은 아닙니다.

## 예상 질문과 답변

### A가 B0보다 낮은데 프로젝트가 실패한 것 아닌가요?

원래 정확도 개선 가설은 실패했습니다. 구현한 검사 흐름과 재현 가능한 평가는
작동했지만, 둘을 합쳐 성능 성공이라고 표현하지 않습니다.

### A+는 원래 A의 개선 결과인가요?

아닙니다. A+는 실행을 다시 하지 않고 저장된 B0·A 출력으로 구성한 dev
후분석 후보입니다. p-value가 0.0625이고 held-out 미검증이므로 성능 개선을
입증했다고 말하지 않습니다.

### 왜 `ABSTAIN`을 오답으로 계산했나요?

보류를 정확도 분모에서 제외하면 실제 자동 처리 성능이 높게 보입니다. 전체 검사
요청을 분모로 고정하고, 자동 판정분의 선택적 정확도는 coverage와 함께만
보고했습니다.

### RAG 검색이 나아졌는데 왜 최종 정확도는 낮았나요?

RAG는 VLM이 만든 관찰문을 기준서와 연결합니다. VLM이 이미지에서 결함을 놓치면
RAG가 픽셀 정보를 새로 만들어 복구할 수는 없습니다. RAG hit rate와 종단 정확도를
분리해 해석했습니다.

### 왜 판정 규칙을 풀어서 정확도를 올리지 않았나요?

근거가 부족한 상태를 PASS나 REJECT로 바꾸면 수치는 올라갈 수 있지만 정상 오탐이나
결함 미검을 확정 판정으로 바꾸게 됩니다. 안전 계약을 유지하고, 별도의 A+ 후보로
탐색 결과를 분리했습니다.

### 왜 held-out을 실행하지 않았나요?

원래 A가 dev 성능 게이트를 통과하지 못했습니다. 이 상태에서 held-out을 반복
사용하면 최종 평가 데이터가 튜닝 데이터가 됩니다. 현재 held-out 계획은
B0/B1/A로 고정돼 있으므로 A+를 포함하려면 별도 후속 평가 계획을 먼저
동결해야 합니다.

### 가장 먼저 바꿀 부분은 무엇인가요?

판정 규칙보다 앞단 시각 모델을 먼저 바꿔야 합니다. 강한 Observer, 서로 다른
Cross 모델, PatchCore 같은 전용 이상탐지 신호를 독립 실험으로 비교하는 것이
우선입니다.
